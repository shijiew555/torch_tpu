# E1 report - Hugging Face training and inference on TPU

Tested against the installed package: torch_tpu 0.3.0, torch 2.14.1+cpu,
libtpu 0.0.50, transformers 5.22.1, accelerate 1.15.0 (and 1.16.0 in a side
dir), peft 0.21.3.
Main was checked by source reading (`git show upstream/main:...`).
All scripts are in `/root/torch_tpu/.claude/tmp/E1/`.
Run commands from that folder.

## Summary

The common HF path works well on TPU.
Training, `generate`, bf16, LoRA and `torch.compile` all match CPU for 21
model types.
I found one torch_tpu bug that is cheap to fix (finding 1).
Findings 2 and 3 are integration gaps on the HF side (transformers or
accelerate), not torch_tpu bugs.
Finding 4 is a mismatch between the docs and how `torch.compile` acts.

## Finding 1 - `torch.autocast("tpu")` uses float16 by default, but the docs say bfloat16 (CONFIRMED)

* Repro: `autocast_default.py`

```python
import torch, torch_tpu
print("torch.tpu._get_autocast_dtype():", torch.tpu._get_autocast_dtype())
print("torch.get_autocast_dtype('tpu'):", torch.get_autocast_dtype("tpu"))
a = torch.randn(4, 4, device="tpu"); b = torch.randn(4, 4, device="tpu")
with torch.autocast("tpu"):
    print("mm dtype under torch.autocast('tpu'):", (a @ b).dtype)
with torch.autocast("cpu"):
    print("mm dtype under torch.autocast('cpu'):", (a.cpu() @ b.cpu()).dtype)
x = torch.full((4, 4), 300.0, device="tpu")
with torch.autocast("tpu"):
    print("300x300 sum of 4 under autocast('tpu'):", (x @ x).float().cpu()[0, 0].item())
```

* Command: `flock /root/tpu.lock timeout 300 python autocast_default.py`
* Actual:

```text
torch.tpu._get_autocast_dtype(): torch.bfloat16
torch.get_autocast_dtype('tpu'): torch.float16
mm dtype under torch.autocast('tpu'): torch.float16
mm dtype under torch.autocast('cpu'): torch.bfloat16
300x300 sum of 4 under autocast('tpu'): inf
```

* Expected: bfloat16, and the result 360000.0.
  `docs/api_reference.md:103` says `torch.amp.autocast("tpu", ...)` uses
  "`bfloat16` by default on TPU".
  The Python class attribute also says bf16.
* With HF models: `torch.autocast("tpu")` with no dtype gives float16
  logits.
  With the default dtype, BERT/T5 (LayerNorm) also hit #5678.
* Root cause: `torch.autocast.__init__` reads
  `torch.get_autocast_dtype("tpu")`.
  That value is the C++ per-thread autocast dtype for PrivateUse1.
  PyTorch core sets it to float16 by default.
  torch_tpu only sets a Python class attribute
  (`src/torch_tpu/_internal/device/_device_module.py:414`,
  `_autocast_dtype = torch.bfloat16`).
  Nothing sends that value to the C++ state.
  `_set_autocast_dtype` (line 920) also changes only the Python attribute.
  Test gap: `tests/amp_test.py:34` (`test_bfloat16_is_preferred`) checks
  `torch.tpu._get_autocast_dtype()`, not `torch.get_autocast_dtype("tpu")`.
  `tests/device/device_module_testing.py:79` expects float16 from the same
  method, so the two tests do not agree.
* Fix: set the C++ autocast dtype for PrivateUse1 to bf16 when torch_tpu
  loads (`at::autocast::set_autocast_dtype(at::kPrivateUse1, at::kBFloat16)`,
  or `torch.set_autocast_dtype("tpu", torch.bfloat16)`).
  Caution: this value is per thread.
  I checked that a new thread gets the core default again.
  A Python fix at import covers only the main thread.
  A full fix may need C++ (for example, set it in the TPU device guard or
  thread init), or a change in PyTorch core so that PrivateUse1 can register
  a default.
  Fix size: small.
  Python-only covers most users. Per-thread coverage needs C++.
* Test: `torch.get_autocast_dtype("tpu") == torch.bfloat16`, also in a new
  thread.
  `torch.autocast("tpu")` matmul output dtype is bf16.
* Overlap: none.
  Searched issues and PRs for "autocast", "autocast default dtype" and
  "autocast float16".
  Related only: #5678 (layer_norm under autocast) and PR 5691.
  Not fixed on main (same code at afd6943a).
* Impact: medium.
  It goes against the docs.
  fp16 overflows at 65504, where bf16 does not.
  Users who copy CUDA code (`with torch.autocast("tpu"):`) silently get fp16.

## Finding 2 - HF `Trainer(torch_compile=True)` cannot run on TPU (CONFIRMED, HF side)

* Repro: `peft_ac.py` (function `trainer_bf16_compile`), with accelerate
  1.16.0 from `acc116/`.
* Commands:
  * `PYTHONPATH=$PWD/acc116 flock /root/tpu.lock timeout 1200 python peft_ac.py "" trainer_bf16_compile`
  * `PYTHONPATH=$PWD/acc116 flock /root/tpu.lock timeout 1200 python peft_ac.py tpu trainer_bf16_compile`
* Actual:
  * Default backend: transformers sets `torch_compile_backend="inductor"`
    (`transformers/training_args.py:1593`).
    torch_tpu then blocks it:
    `BackendCompilerFailed: backend='inductor' raised: RuntimeError:
    torch.compile(..., backend='inductor') on TPU is experimental ...
    Pass backend='tpu' ...`.
  * `torch_compile_backend="tpu"`: accelerate rejects it.
    The error is `ValueError: 'TPU' is not a valid DynamoBackend`
    (`accelerate/utils/dataclasses.py:1016`).
* Expected: the Trainer compiles with the TorchTPU backend.
* Workaround (it works): call `model.compile()` before you make the
  `Trainer`, and do not set `torch_compile`.
  Script `trainer_manual_compile.py` prints
  `manual compile Trainer OK train_loss=5.5551 eval_loss=5.5459`.
* Main of both HF repos (checked with `gh api`): transformers still sets
  "inductor" by default, and the accelerate `DynamoBackend` enum has no TPU
  member.
* Fix: on the HF side.
  transformers should set the default backend to "tpu" when
  `is_torch_tpu_available()`, and accelerate needs a `TPU` DynamoBackend.
  The fix is small but it is not in torch_tpu.
  An issue in torch_tpu that tracks the ecosystem gap (like #6127) is
  possible.
* Overlap: none found in torch_tpu, transformers or accelerate.
* Impact: medium. `torch_compile=True` is a common Trainer flag.

## Finding 3 - accelerate 1.15.0 does not detect TPU, so Trainer crashes (CONFIRMED, fixed in accelerate 1.16.0)

* Repro: `trainer2.py`.
* Command: `flock /root/tpu.lock timeout 600 python trainer2.py`
* Actual (accelerate 1.15.0):

```text
TrainingArguments.device: tpu:0 n_gpu: 1 accelerate state device: cpu
Trainer FAIL RuntimeError embedding(): expected tensor to be on tpu, got cpu
```

  transformers moves the model to `tpu:0`, but accelerate moves the batches
  to `cpu`.
  `from_pretrained(device_map="auto")` also loads on CPU (`devmap.py`).
* With accelerate 1.16.0 (`PYTHONPATH=$PWD/acc116`): the Trainer trains,
  and `device_map="auto"` gives `tpu:0`.
  The fix is huggingface/accelerate PR 4547 (merged 2026-11-13).
  With 1.15.0, `ACCELERATE_TORCH_DEVICE=tpu` is a workaround.
* torch_tpu action: none in code.
  A docs note "use accelerate >= 1.16.0" may help.
  torch_tpu has no `accelerate` pin or doc today.
* Impact: low now (fixed upstream). Pip users with an older accelerate can
  still hit it.

## Finding 4 - `torch.compile(model)` on TPU recompiles for each new sequence length; docs and an error message say default dynamism is bounded (CONFIRMED behavior; docs issue)

* Repro: `dyn_backend.py`, `dynseq.py` (HF Llama training).
* Commands:
  * `flock /root/tpu.lock timeout 600 python dyn_backend.py`
  * `TORCH_LOGS=recompiles flock /root/tpu.lock timeout 900 python dynseq.py`
* Actual:
  * `x*2` over 5 lengths: 5 graphs.
    The doc's own `torch.cat` decode loop with `torch.compile(cat)` (no
    `dynamic=` argument): 8 graphs in 8 steps.
  * HF Llama compiled training with sequence lengths 16, 20, 24, 28, 32,
    17: 6 graphs.
    The guard message is `size mismatch at index 1. expected 16, actual 20`.
    After `recompile_limit` (8), Dynamo stops compiling that frame and runs
    it eagerly.
    `dyn_limit.py` confirms this. At L=24 the log shows
    `torch._dynamo hit config.recompile_limit (8)`, and `unique_graphs`
    stays at 8 after that.
* Cause: `src/torch_tpu/_loader.py:150-159` (`_default_tpu_compile`) sets
  `dynamic=False` when the caller does not pass `dynamic`.
  This is on purpose (commit 0e477085, 2026-10-07).
  But two texts say the opposite:
  * The error in `src/torch_tpu/_internal/compile/_backend.py:957-962`
    says "dynamic=None or default dynamism i.e. torch.compile(model)".
  * `docs/dynamic_shapes.md` ("How dynamic shapes are handled") calls
    `dynamic=None` "default dynamism".
  Only an explicit `dynamic=None` gives bounded dynamism.
* Fix: Python and docs only.
  Fix the error message and the doc wording.
  Optionally, log one warning when a TPU frame recompiles because of a
  shape change, with the hint "pass dynamic=None or mark_dynamic".
* Overlap: #5000 and #5086 are about recompiles from storage offset and
  index, not this default.
  None found for this mismatch.
* Impact: low to medium.
  Training with dynamic padding (`DataCollatorWithPadding`) recompiles for
  each new length.

## Finding 5 - a failed lazy op makes a later, unrelated `model.to("tpu")` raise (CONFIRMED, cause is a hypothesis)

* Repro: `error_leak3.py`.
  It uses the known #5678 lowering failure as the trigger.
* Command: `flock /root/tpu.lock timeout 300 python error_leak3.py`
* Actual:

```text
bert forward returned (lazy)
loc("layer_norm/layer_norm"): error: 'stablehlo.multiply' op requires compatible types ...
unrelated t5 .to('tpu') FAILED: RuntimeError failed to inline functions in MLIR module
small op: [2.0, 2.0, 2.0]
```

  The BERT forward fails, but its result is never read.
  Then a new T5 model `.to(torch.bfloat16).to("tpu")` raises the BERT
  error.
  A small op after that works, so the error does not stay.
  A minimal version with only one LayerNorm does not leak
  (`error_leak.py`, `error_leak2.py`).
* Hypothesis: `Module.to` (a large batch of H2D copies) flushes the pending
  lazy graph.
  The flush then reports the error of an op from another graph.
  The message has no op name (`root_op_name=''`).
* Impact: low.
  Users see a wrong location for a real failure.
  #5678 already notes that "Python only sees ... at the next
  materialization".
  Report only as an extra detail on #5678 or a new issue about error
  attribution.

## Tried, works (skip in later rounds)

* Forward, backward and 3 AdamW steps, eager and `torch.compile`, match
  CPU (loss diff about 1e-4).
  Models: Llama, GPT-2, BERT, T5, Qwen2, Gemma, Mistral (sliding window),
  Gemma2, Gemma3, Phi3, Mixtral MoE, Qwen3, Qwen3-MoE, RoBERTa, DeBERTa-v2,
  ViT, CLIP, Whisper, BART, ConvNeXt, ResNet.
* `generate`: greedy, no cache, beam, beam with `num_return_sequences`,
  sampling (top-k/top-p), left padding with `attention_mask`, static cache,
  static cache with compiled forward, compiled forward with dynamic cache,
  repetition penalty, no_repeat_ngram, bad_words, min_new_tokens with eos,
  multiple eos, suppress_tokens, output_scores, output_hidden_states.
  All match CPU tokens.
  The first call compiles each step (about 10 s for 20 tokens).
  Later calls are fast (0.1 to 0.9 s).
* bf16 weights: training and generate work.
  Small differences are bf16 near-ties.
* `torch.autocast("tpu", dtype=torch.bfloat16)`: Llama/GPT-2/T5 work, eager
  and compiled.
  BERT fails because of #5678 (claimed).
* SDPA and eager attention, gradient checkpointing, labels with -100,
  sequence length 1024/2048, save_pretrained/from_pretrained with
  `device_map="tpu"`, PEFT LoRA training and merge_and_unload, Trainer
  (bf16) with accelerate 1.16.0, Trainer evaluate.

## Dead ends (one line each)

* Mismatches in MoE and bf16 greedy decoding: near-ties from the default
  TPU matmul precision.
  With `torch.set_float32_matmul_precision("highest")` they match.
* ResNet BatchNorm weight grad rel diff 0.55: conv default precision plus
  ReLU sign flips.
  With "highest" the diff is 4e-7. BatchNorm alone is exact.
* T5 loss diff at first: attention dropout was on (my test bug).
* `attn_implementation="flex_attention"` raises `NameError:
  create_block_mask`.
  transformers turns off flex on TPU on purpose (`import_utils.py:761`).
  This is a transformers error-message bug, and flex is in flight in torch_tpu
  (PRs 6509/6511).
* Once, `/dev/vfio/0 already opened by another process` while I held the
  lock.
  The holder was not found later. Maybe another agent ran without the lock.
