## Result

* 1 confirmed bug with high impact: DataLoader worker processes take the
  TPU away from the training process.
  Cause: `torch.manual_seed()` initializes the TPU, and every DataLoader
  worker calls it.
* Autograd features, profiler, memory stats, deterministic mode, printing
  and `assert_close` work. See "Tried, works".
* Two re-checks: `torch.Stream("tpu")` is still broken on main (source
  reading). The dynamism doc wording is unchanged on main.

## Finding 1 - DataLoader `num_workers>0` takes the TPU when the parent has not used it yet (CONFIRMED)

* Repro: `$COORD/scratch/S3-E4/dl_seed_repro.py`

```python
import faulthandler, sys; faulthandler.dump_traceback_later(120, exit=True)
import torch
import torch_tpu  # noqa: F401

class DS(torch.utils.data.Dataset):
    def __len__(self): return 8
    def __getitem__(self, i): return torch.full((4,), float(i))

if __name__ == "__main__":
    persistent = sys.argv[1] == "persistent"
    model = torch.nn.Linear(4, 1)  # built on CPU, moved later
    dl = torch.utils.data.DataLoader(DS(), batch_size=4, num_workers=2,
                                     persistent_workers=persistent)
    for step, b in enumerate(dl):
        if step == 0:
            model.to("tpu")
        print("step", step, "loss", model(b.to("tpu")).sum().item())
    print("OK")
```

* Command (both `persistent` and `nonpersistent` fail):
  `flock /root/tpu.lock timeout 150 <venv>/bin/python dl_seed_repro.py persistent`
* Actual (log `dl_seed_persistent.log`): in a worker,
  `device_gen_impl.cc:801] FAILED_PRECONDITION: skipping seeding the TPU
  generators because TPU initialization failed ... Colliding process(es):
  PID 159962 (... -c import sys; from multi...)`.
  Then the parent fails at `model.to("tpu")`:
  `RuntimeError: [TorchTPU] Failed to acquire a TPU device node
  '/dev/vfio/0' because it is already opened by another process on this
  host. Colliding process(es): - PID 159962 (... multiprocessing worker)`.
  Exit code 1. No training step runs.
* Expected: `step 0 ... step 1 ... OK`. On CUDA, workers never initialize
  the GPU (`torch.cuda.manual_seed_all` is queued with `_lazy_call`).
* Second symptom, also when the parent uses the TPU first
  (`dl_repro.py tpu_first`): training works, but every worker start
  prints the full "Failed to acquire ... Colliding process ...
  Remediation: set TPU_VISIBLE_DEVICES" block (about 12 lines per worker,
  again each epoch for non-persistent workers). The remediation text is
  wrong for this case.
* Proof that seeding is the trigger (`seed_repro.py`): parent holds the
  TPU. A child that runs `import torch, torch_tpu` prints no collision.
  A child that then runs `torch.manual_seed(1)` prints the collision block
  between "before seed" and "after seed".
  DataLoader `_worker_loop` calls `torch.manual_seed(seed)`, which calls
  `torch.tpu.manual_seed_all`.
* Root cause (upstream/main):
  `csrc/eager/device_gen_impl.cc` `InitializeTpuForSeeding()` (called by
  `SetManualSeed` / `SetManualSeedAll`) calls
  `PjrtBackend::GetInstance().EnsureInitialized()`.
  So seeding opens `/dev/vfio/0`. The first process that seeds owns the
  TPU. The code has `TODO: b/572861883 - Defer seeding until the TPU is
  initialized, instead of initializing the TPU here.`
  Python entry: `src/torch_tpu/_internal/device/_device_module.py`
  `manual_seed_all()` (calls `is_available()` then the C++ seed).
  Commit 7dbbd52fb (in `afd6943a`) made seeding skip with a warning on
  failure, but kept "When TPU initialization happens is unchanged".
* Python versions: confirmed with `forkserver` (Python 3.14 default).
  Hypothesis: with `fork` (Python <= 3.13 default), the same happens when
  the parent has not initialized the TPU before the fork, because
  `_is_in_bad_fork()` is false then.
* Fix idea: defer seeding when the TPU is not initialized. Store the seed
  (like `torch.cuda._lazy_call`) and apply it when the generators are
  created. C++ (device_gen_impl.cc) plus maybe Python, about 50-100 lines
  plus tests. A smaller Python-only option: in `manual_seed`/
  `manual_seed_all`, if `not torch.tpu.is_initialized()`, keep the seed in
  a queue that the first TPU init applies. Needs an init hook; size not
  checked.
* Test: start a DataLoader with `num_workers=2` before any TPU use, then
  use the TPU in the loop. Expect no error and no collision text on
  stderr. Also: seeding in a fresh process does not make
  `torch.tpu.is_initialized()` true.
* Overlap: #3890 (closed, fork deadlock, fixed by PR #3976
  `_is_in_bad_fork`) is a different path. #4166 (closed) is about abort
  vs raise. No issue or PR about seeding in workers. Searched: "DataLoader
  num_workers", "manual_seed initializes TPU", "DataLoader worker TPU
  device", "already opened by another process", "lazy seed".
  Internal bug b/572861883 is named in the TODO (not public).
* Impact: high. `num_workers>0` is the normal input pipeline. Any script
  that builds the DataLoader iterator before its first TPU op crashes.
  All other scripts get error spam with a misleading remediation.

## Finding 2 - TPU profiler adds about 1500 `MutexLock` host events per small step (CONFIRMED, low)

* Repro: `$COORD/scratch/S3-E4/prof.py` (MLP SGD step inside
  `profile(activities=[CPU, PrivateUse1])`). Log `prof.log`.
* Actual: profiling works (TPU kernel times, `record_function`,
  `key_averages`, chrome trace, `tensorboard_trace_handler` all fine).
  But the chrome trace has 1974 `cpu_op` events vs 44 with CPU only:
  513 each of `MutexLock`, `MutexLock::Acquire`, `MutexLock::Release`,
  plus PJRT internals.
* Expected: host events at the PyTorch op level, as with CUDA.
* Root cause (hypothesis): `csrc/internal/profiler/tpu_profiler_plugin.cc`
  `TpuKinetoProfilerSession::start()` uses
  `tsl::ProfilerSession::DefaultOptions()` (host tracer level 2). Users
  can override it with `host_tracer_level` in the custom config, but the
  default is noisy. Python? No, C++. Small (1-5 lines) if level 1 is the
  right default; needs a maintainer decision.
* Overlap: none found ("profiler MutexLock", "host_tracer_level").
* Impact: low. Traces are larger and harder to read; nothing breaks.

## Tried, works (TPU matches CPU)

* Autograd: tensor `register_hook` (grad change), module
  `register_forward_pre_hook`, `register_full_backward_hook`,
  `register_full_backward_pre_hook`, `register_post_accumulate_grad_hook`,
  `saved_tensors_hooks` (pack to CPU), `save_on_cpu(pin_memory=True/False)`,
  `detect_anomaly` (same NaN error), `autograd.grad` with `allow_unused` and
  `materialize_grads`, `is_grads_batched`, forward-mode AD
  (`make_dual`, linear, softmax), inference tensors used later (same
  errors), `retain_grad`, `requires_grad_` on a view, custom
  `autograd.Function`, double backward, `gradcheck` f64, non-reentrant
  checkpoint without dropout.
* `use_deterministic_algorithms(True)`: index_put accumulate, scatter_add,
  index_add, cumsum, embedding backward, bincount, bilinear interpolate
  backward. No error or warning. `empty` gets NaN fill like CPU.
* `torch.backends` flags (cudnn/mps False, cuda matmul tf32 False,
  `current_accelerator`, `is_autocast_available("tpu")`).
* Profiler with CPU only and with TPU activity; schedule plus
  `tensorboard_trace_handler`.
* `torch.accelerator` memory: `empty` allocates nothing until written
  (lazy), fill/ones/add add 256 MiB each, `del` frees, peak and
  `reset_peak_memory_stats` correct, `get_memory_info` works.
  `memory_stats()` cumulative `allocated`/`freed` counters stay 0 (only
  current/peak come from PJRT, `tensor_to_buffer.cc:548`). Minor.
* `torch.multiprocessing.spawn` worker that uses the TPU (parent did not
  use it): works.
* Printing: large (summarized, same as CPU), bf16, fp8, f64, complex,
  empty, non-contiguous, inf/nan, scalar, grad_fn, small values in sci
  mode, `set_printoptions`.
* `torch.testing.assert_close` (TPU vs TPU, mismatch message, mixed device
  message, `check_device=False`).
* `.numpy()` and `np.asarray` give the clear "Use Tensor.cpu()" error;
  `numpy(force=True)` works. pickle, hash, `share_memory_` (no-op),
  `untyped_storage`, `float()`/`bool()`.
* Sparse COO: `.to("tpu")`, add, `to_dense`, `.cpu()`, values work;
  `sparse.mm` gives the clear "sparse operators are not supported on TPU
  yet". Nested jagged layout: `sin` works.

## Dead ends

* `torch.tpu.synchronize()` raises "internal to TorchTPU ... use
  torch.accelerator.synchronize": on purpose.
* TPU tensor through `mp.Queue`: the feeder thread prints
  "_share_fd_: only available on CPU" and the receiver waits forever.
  Upstream torch `reductions.py` behavior for every non-CUDA device.
* `save_on_cpu(pin_memory=True)` DeprecationWarning for
  `pin_memory(device)`: covered by the pin_memory task. Also
  `save_on_cpu` defaults to `device_type="cuda"`, so it does not pin on
  TPU unless `device_type="tpu"` is passed (upstream torch API).
* `pin_memory_device="tpu"`: torch prints its own "pin_memory_device is
  deprecated" warning. Upstream.
* Sparse CSR `.to("tpu")` and strided nested `sin`: raw dispatcher
  `NotImplementedError` (backend `SparseCsrtpu` / `NestedTensortpu`). Rare
  use; a clearer message would be nice. Not reported as a finding.
* `torch.from_dlpack` of a TPU tensor: clear `ValueError: Unknown device
  type tpu for Dlpack`.
* Not done in time: `pin_memory=True` DataLoader rerun with the parent
  using the TPU first (earlier runs were broken by Finding 1).
