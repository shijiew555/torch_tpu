Status: done, 2026-11-18T04:10Z.

Versions tested: installed 0.3.0, and upstream/main Python (afd6943a) on the

## Results first

* 3 confirmed findings. None is in the claimed list, open PRs, or issues.
* Finding 1 is the best candidate: silent wrong semantics, Python-only fix.
* Finding 2 (`torch.cond` / `while_loop`) is a feature gap. A full fix needs

* The compile backend is robust. 50+ common patterns pass (list at the end).

## Finding 1 - Compiled outputs that alias each other lose the alias (inference)

Confirmed on 0.3.0 and upstream/main.

What happens: a compiled function returns an intermediate `y` and a view of
`y`. No input requires grad. With `backend="tpu"`, the view is a separate
buffer. An in-place change to `y` does not show in the view. Eager TPU,
CPU eager, `aot_eager`, and `inductor` all keep the alias.
With `requires_grad=True` the alias is kept (AOTAutograd regenerates it).

Repro: `/root/torch_tpu/.claude/tmp/E2/alias_repro.py`

```python
import torch
import torch_tpu  # noqa: F401

def f(x):
    y = x * 2
    return y, y.view(2, 8), y[1:]

def check(device, backend, requires_grad=False):
    torch._dynamo.reset()
    x = torch.arange(16.0).view(4, 4).to(device).requires_grad_(requires_grad)
    fn = torch.compile(f, backend=backend) if backend else f
    a, b, c = fn(x)
    shared = (a.untyped_storage().data_ptr() == b.untyped_storage().data_ptr()
              and a.untyped_storage().data_ptr() == c.untyped_storage().data_ptr())
    with torch.no_grad():
        a.add_(100)
    print(f"{device} backend={backend!s:9s} requires_grad={requires_grad!s:5s}"
          f" shared={shared!s:5s} b[0,:3]={b[0, :3].tolist()}"
          f" c[0,:3]={c[0, :3].tolist()}")

check("cpu", None); check("cpu", "aot_eager"); check("tpu", None)
check("tpu", "tpu"); check("tpu", "tpu", requires_grad=True)
```

Command:

```bash
cd /root/torch_tpu/.claude/tmp/E2
PYTHONPATH=/root/torch_tpu/.claude/tmp/E6/overlay_main \
  flock /root/tpu.lock timeout 600 python alias_repro.py
```

Actual output (same on 0.3.0 without PYTHONPATH):

```
cpu backend=None      requires_grad=False shared=True  b[0,:3]=[100.0, 102.0, 104.0] c[0,:3]=[108.0, 110.0, 112.0]
cpu backend=aot_eager requires_grad=False shared=True  b[0,:3]=[100.0, 102.0, 104.0] c[0,:3]=[108.0, 110.0, 112.0]
tpu backend=None      requires_grad=False shared=True  b[0,:3]=[100.0, 102.0, 104.0] c[0,:3]=[108.0, 110.0, 112.0]
tpu backend=tpu       requires_grad=False shared=False b[0,:3]=[0.0, 2.0, 4.0] c[0,:3]=[8.0, 10.0, 12.0]
tpu backend=tpu       requires_grad=True  shared=True  b[0,:3]=[100.0, 102.0, 104.0] c[0,:3]=[108.0, 110.0, 112.0]
```

Expected: the `backend=tpu requires_grad=False` row matches the others
(`shared=True`, `b[0,:3]=[100.0, 102.0, 104.0]`).
The inductor result was also checked (`alias_outputs.py inductor`): shared.

Root cause (confirmed by code reading):

* AOTAutograd regenerates output aliases only for outputs that require grad.
  For non-grad outputs it marks them `OutputType.non_alias` and trusts the
  backend to keep views
  (`torch/_functorch/_aot_autograd/collect_metadata_analysis.py`, final
  `else: output_type = OutputType.non_alias`). Inductor keeps them with
  `reinterpret_tensor`.
* torch_tpu makes one fresh device buffer per graph output.
  `_process_fx_outputs` dedups outputs only when data_ptr AND full layout
  (shape, stride, offset) are equal
  (upstream/main `src/torch_tpu/_internal/export/export.py:389`
  `_TensorDedupeKey`, `:414` `_process_fx_outputs`, `:461`).
  Views with a different layout become separate outputs.
  The C++ `FxOutputReconstructor` (`csrc/internal/compile/tpu_torch_compile.cc`)
  only maps deduped indices.
* The AOT forward graph confirms it: it returns `mul` and
  `aten.view(mul, [2, 8])` as two plain outputs (`alias_min.log`,
  `TORCH_LOGS=aot_graphs`).

Fix (Python-only, medium, about 50-100 lines plus test):

* In `_process_fx_outputs`, group tensor outputs by storage. When an output
  shares storage with an earlier output that covers the whole storage, do not
  emit it as an MLIR output. Record (base index, size, stride, offset), and
  after reconstruction return `base.as_strided(size, stride, offset)`.
  This can wrap the C++ reconstructor in Python. It also saves one device
  buffer and one output per alias.
* The case where only views are returned (`return y[0], y[1:]`, `y` not
  returned) needs the base added as a hidden extra output. Confirmed this case
  also loses the alias (`sweep3_main.log`, `alias_two_views_of_intermediate`).

Test idea: in a compile test, return `(y, y.view(...), y[1:])` with no grad,
mutate `y` in place, check the views see it and share `untyped_storage()`.
Compare with `aot_eager`. Run under `flock`.

Overlap: none. Searched issues/PRs for "alias output", "output aliasing",
"aliased outputs". PR 6497 (autodonate base buffers on view writes) is eager
`CopyTpuToTpu`, not compile outputs.

Impact: medium. Silent wrong results, no error. Affects inference-mode
compiled code that returns a tensor and its views, then writes in place
(for example caches, buffers, `unbind` / `split` outputs).

## Finding 2 - `torch.cond` and `while_loop` with a tensor predicate fail under backend="tpu"

Confirmed on 0.3.0 and upstream/main.

Repro: `/root/torch_tpu/.claude/tmp/E2/cond_repro.py`

```python
import torch
import torch_tpu  # noqa: F401

def f(x):
    return torch.cond(x.sum() > 0, lambda t: t.sin(), lambda t: t.cos(), (x,))

x = torch.rand(4)
print("cpu eager   :", f(x))
print("tpu eager   :", f(x.to("tpu")).cpu())
print("cpu compiled:", torch.compile(f, backend="aot_eager")(x))
print("tpu compiled:", torch.compile(f, backend="tpu")(x.to("tpu")).cpu())
```

Command:

```bash
cd /root/torch_tpu/.claude/tmp/E2
PYTHONPATH=/root/torch_tpu/.claude/tmp/E6/overlay_main \
  flock /root/tpu.lock timeout 600 python cond_repro.py
```

Actual output (log `cond_main.log`):

```
cpu eager   : tensor([0.1913, 0.4569, 0.7961, 0.0663])
tpu eager   : tensor([0.1913, 0.4569, 0.7961, 0.0663])
cpu compiled: tensor([0.1913, 0.4569, 0.7961, 0.0663])
torch._dynamo.exc.BackendCompilerFailed: backend='tpu' raised:
RuntimeError: local_scalar_dense(): cannot materialize a tensor during a
stream-isolated copy, materialization requires an active stream
While executing %cond : ... torch.ops.higher_order.cond ...
```

Expected: the compiled TPU result equals the eager result.
Same error for `torch._higher_order_ops.while_loop.while_loop` with a tensor
loop condition (`sweep3_main.log`, `while_loop_compiled`).
`torch.cond` with a Python bool predicate works (Dynamo removes the cond).

Root cause (confirmed by trace and code reading):

* `fx_to_mlir` runs the AOT graph with placeholder tensors
  (upstream/main `src/torch_tpu/_internal/export/export.py:288`
  `EagerLikeFxInterpreter.run_node`).
* There is no TPU lowering for `higher_order.cond` or `while_loop`. The HOP
  falls to `cond_op_dense` (`torch/_higher_order_ops/cond.py:309`), which does
  `if pred:` on a placeholder.
* `scan` and `associative_scan` do have a lowering
  (`src/torch_tpu/_internal/compile/scan.py`, C++ `create_scan_op`), so the
  pattern exists. No `create_cond_op` or `create_while_op` exists in `csrc`.

Fix options:

* Full fix: C++ op that builds `stablehlo.case` / `stablehlo.while`, plus a
  Python HOP impl like `scan.py`. Needs a build. Large.
* Python-only option for `cond`: in the HOP impl, run both branches on
  placeholders and select with `torch.where(pred, true_out, false_out)`.
  Correct for pure branches, but runs both. Maintainers may not want it.
* Minimum: raise a clear `NotImplementedError` naming `torch.cond` and
  suggesting eager or a graph break. Python-only, small.

Overlap: none. No issue or PR for cond/while_loop compile. PR 6470 is about
the Pallas FX verifier, not this lowering.

Impact: medium-low. `torch.cond` is the documented way to keep data-dependent
control flow in one graph (also needed for `torch.export`). Eager works.

## Finding 3 - Slice length from `.item()` gives an internal error (capture_scalar_outputs)

Confirmed on upstream/main. Hypothesis: same on 0.3.0 (same code path).

Repro: `/root/torch_tpu/.claude/tmp/E2/item_slice_repro.py`

```python
import torch
import torch_tpu  # noqa: F401

torch._dynamo.config.capture_scalar_outputs = True

def f(x, n):
    k = n.item()
    return x[:k].sum()

x = torch.arange(8.0)
n = torch.tensor(5)
print("cpu aot_eager:", torch.compile(f, backend="aot_eager")(x, n))
print("tpu compiled :", torch.compile(f, backend="tpu")(x.to("tpu"), n.to("tpu")).cpu())
```

Actual (log `item_main.log`): `cpu aot_eager: tensor(10.)`, then
`BackendCompilerFailed ... RuntimeError: local_scalar_dense(): cannot
Materialize() a placeholder tensor or a tensor that depends on a
placeholder.` from `export.py:288` via `split_compiler.py` `compile_submod`.

Expected: `tensor(10.)`, or a clear message. `split_compiler.py`
`compile_submod` already gives a clear message for the CPU-tensor case
("... data-dependent shapes ... disabling capture_dynamic_output_shape_ops
and capture_scalar_outputs"), but not for this TPU-tensor case.
`.item()` used as a scalar (not a shape) works.

Fix: Python-only, small: detect unbacked SymInts in the TPU submodule and
raise the same clear message. Real support needs bounded dynamism work.

Impact: low. Non-default config flag, known-hard pattern. Related area:
#5085 (nonzero compile time), #6112 (bounded dynamism deny list).

## Tried, works (skip in later rounds)

On TPU with `backend="tpu"`, results match CPU (0.3.0; sweep3 also on main):

* Graph breaks: `print`, `.item()` (default config), data-dependent `if`,
  `nonzero`, boolean mask index, `torch.compiler.disable` inside.
* Mutation: in-place on input, on input view, on transposed input, on slice
  input (storage offset), buffer mutation in module forward, EMA param update
  under `no_grad`, mutate then return view of input, mutate returned input view.
* Context: `no_grad` inside and outside, `inference_mode` inside and outside,
  `requires_grad` change (recompile), autocast bf16 inside compile.
* Outputs: return input itself, views of inputs, int/bool outputs.
* Dynamism: `mark_dynamic` forward, backward, reshape/transpose, in-place
  input, returned dynamic slice. dtype change recompiles. Python int/float
  args. kwargs and `None` args.
* Autograd: `autograd.grad(create_graph=True)` inside compiled region,
  `retain_graph`, `detach`, custom `autograd.Function` with `fullgraph=True`,
  non-reentrant `checkpoint` inside compile, grad accumulation, SDPA causal
  backward, compiled AdamW step, `module.compile()` with forward hook,
  train/eval switch with dropout.
* RNG: dropout stats, `manual_seed` reproducibility of `rand_like`.
* Complex: `view_as_complex` / `view_as_real` round trip.
* Default backend (inductor) on TPU tensors: works.

## Dead ends (one line each)

* `dynamic=True` raises a clear `NotImplementedError` by design (`_backend.py`).
* Double backward through a compiled graph fails in upstream PyTorch
  (`aot_autograd does not currently support double backward`), all backends.
* `fullgraph=True` with `.item()` does not raise on torch 2.14, also on CPU
  `backend="eager"`. Upstream PyTorch behavior.
* `torch.compile` of a CPU-only function opens the TPU device (48 vfio fds).
  Cause: Dynamo `SymbolicStreamState` calls `torch.accelerator.is_available()`
  and `current_stream()`. Upstream PyTorch behavior (CUDA does the same).
  Side effect: run CPU-only compile scripts under the TPU lock too.
* Once, a TPU process hung in futex wait while a second (CPU-only compile)
  process tried to open the TPU. Not reproduced. Not investigated.
* `py-spy` install was denied by the permission system. Use
  `faulthandler.dump_traceback_later` for hang stacks.
